# Геолокационная маршрутизация серверов

## Описание

Добавлена функциональность геолокационной маршрутизации, которая позволяет направлять клиентов на разные серверы в зависимости от их географического положения.

## Изменения

### 1. Структура Server
Добавлено новое поле `Region` в структуру `Server`:

```go
type Server struct {
    Name     string `json:"name"`
    DNS      string `json:"dns"`
    Sessions int    `json:"sessions"`
    Enable   bool   `json:"enable"`
    Online   bool   `json:"online"`
    Region   string `json:"region"` // Region restriction, e.g., "RU" for Russia-only servers
}
```

### 2. Логика маршрутизации (Универсальная)

Логика работает автоматически для **любой страны** без изменений кода:

#### Глобальные серверы (`region: ""`):
- Доступны **всем клиентам** из любой страны
- Участвуют в общем пуле для мониторинга и распределения сессий
- Используются как основной пул для стран без выделенных серверов

#### Региональные серверы (например, `region: "RU"`, `region: "CN"`, `region: "US"`):
- ⚠️ **ИЗОЛИРОВАНЫ** от остальных стран - не попадают в их пул серверов
- ⚠️ **НЕ участвуют** в мониторинге сессий для других стран
- ✅ Доступны **ТОЛЬКО** клиентам с соответствующим `country_code` в POST запросе
- ✅ Для своей страны работают как обычные серверы с мониторингом сессий

#### Правила для клиента:
- Клиент с `country_code: "RU"` видит: **ТОЛЬКО str9** (региональный RU) - глобальные исключены
- Клиент с `country_code: "IL"` видит: **ТОЛЬКО глобальные** серверы - региональные исключены
- Клиент без `country_code` видит: только глобальные серверы

**Ключевая логика:** Если для страны есть хотя бы один региональный сервер, то глобальные серверы для нее полностью исключаются!

### 3. Алгоритм фильтрации серверов

При получении POST запроса с `country_code`, система применяет двухэтапную фильтрацию:

**Этап 1: Сортировка серверов**
```go
for каждый server в конфигурации:
    if server.Region == "":
        добавить server в globalServers
    else if server.Region == country_code:
        добавить server в regionalServers
    else:
        пропустить (сервер другой страны)
```

**Этап 2: Выбор пула**
```go
if есть regionalServers:
    использовать ТОЛЬКО regionalServers (глобальные исключены)
else:
    использовать ТОЛЬКО globalServers
```

**Ключевой момент:** Наличие хотя бы одного регионального сервера для страны **полностью исключает** глобальные серверы из пула для этой страны. Это изолирует региональный трафик.

### 4. Функции

#### `getBestServerForClient(countryCode, clientIP string)`
Новая функция, которая выбирает оптимальный сервер с учетом кода страны клиента.

**Параметры:**
- `countryCode` - двухбуквенный код страны (ISO 3166-1 alpha-2), например "RU", "US", "IL"

**Логика работы:**
1. Фильтрует серверы по региону на основе кода страны
2. Выбирает сервер с минимальным количеством сессий
3. При одинаковом количестве сессий выбирает случайный сервер

#### `getBestServer()`
Оставлена для обратной совместимости. Вызывает `getBestServerForCountry("")`, что означает "без ограничений по региону".

### 5. POST /server
Обработчик `getServerByID` теперь автоматически извлекает код страны из поля `Geo.CountryCode` в теле запроса и использует его для выбора сервера.

## Конфигурация

### Формат конфигурации
Пример `conf.json` с несколькими регионами:

```json
{
  "str1": {
    "name": "str1",
    "dns": "str1.example.com",
    "sessions": 0,
    "enable": true,
    "online": true,
    "region": ""
  },
  "str2": {
    "name": "str2",
    "dns": "str2.example.com",
    "sessions": 0,
    "enable": true,
    "online": true,
    "region": ""
  },
  "str9": {
    "name": "str9",
    "dns": "str9.example.com",
    "sessions": 0,
    "enable": true,
    "online": true,
    "region": "RU"
  },
  "str10": {
    "name": "str10",
    "dns": "str10.example.com",
    "sessions": 0,
    "enable": true,
    "online": true,
    "region": "CN"
  },
  "str11": {
    "name": "str11",
    "dns": "str11.example.com",
    "sessions": 0,
    "enable": true,
    "online": true,
    "region": "US"
  }
}
```

### Параметры региона

- **`region: ""`** (пустая строка) - **глобальный сервер**, доступен для всех клиентов из любой страны
- **`region: "RU"`** - **региональный сервер** для России, доступен **только** клиентам с `country_code: "RU"`
- **`region: "CN"`** - **региональный сервер** для Китая, доступен **только** клиентам с `country_code: "CN"`
- **`region: "US"`** - **региональный сервер** для США, доступен **только** клиентам с `country_code: "US"`

Вы можете использовать любые двухбуквенные коды стран (ISO 3166-1 alpha-2) для создания региональных пулов. Логика применяется автоматически без изменений кода!

## Примеры использования

### Сценарий 1: Клиент из России (RU)
```json
POST /server
{
  "geo": {
    "country_code": "RU",
    "city": "Moscow",
    "region": "Moscow"
  }
}
```
**Доступные серверы в пуле:** 
- ✅ `str9` (region: "RU") - **ЕДИНСТВЕННЫЙ доступный**

**Недоступные серверы (полностью исключены):** 
- ❌ `str1`, `str2`, `str3`... (глобальные) - **исключены, т.к. есть региональный сервер для RU**
- ❌ `str10` (region: "CN")
- ❌ `str11` (region: "US")

**Результат:** вернется **str9** (единственный доступный региональный сервер для RU)

### Сценарий 2: Клиент из Китая (CN)
```json
POST /server
{
  "geo": {
    "country_code": "CN",
    "city": "Beijing",
    "region": "Beijing"
  }
}
```
**Доступные серверы в пуле:** 
- ✅ `str10` (region: "CN") - **ЕДИНСТВЕННЫЙ доступный**

**Недоступные серверы (полностью исключены):** 
- ❌ `str1`, `str2`, `str3`... (глобальные) - **исключены, т.к. есть региональный сервер для CN**
- ❌ `str9` (region: "RU")
- ❌ `str11` (region: "US")

**Результат:** вернется **str10** (единственный региональный сервер для CN)

### Сценарий 3: Клиент из Израиля (IL) - нет выделенных региональных серверов
```json
POST /server
{
  "geo": {
    "country_code": "IL",
    "city": "Tel Aviv",
    "region": "Tel Aviv"
  }
}
```
**Доступные серверы в пуле:** 
- ✅ `str1` (region: "", глобальный)
- ✅ `str2` (region: "", глобальный)

**Недоступные серверы (изолированы):** 
- ❌ `str9` (region: "RU", **исключен** - не попадает в пул для IL)
- ❌ `str10` (region: "CN", **исключен** - не попадает в пул для IL)
- ❌ `str11` (region: "US", **исключен** - не попадает в пул для IL)

**Важно:** Клиент из Израиля **не участвует** в мониторинге и балансировке региональных серверов. Они для него просто не существуют в системе!

### Сценарий 4: Клиент без указания страны или страна не определена
```json
POST /server
{
  "geo": {
    "country_code": "",
    "city": "",
    "region": ""
  }
}
```
**Доступные серверы в пуле:** 
- ✅ `str1` (region: "", глобальный)
- ✅ `str2` (region: "", глобальный)

**Недоступные серверы (изолированы):** 
- ❌ `str9` (region: "RU")
- ❌ `str10` (region: "CN")
- ❌ `str11` (region: "US")

**Итог:** Все региональные серверы **полностью исключены** из пула для клиентов без `country_code`

Для наглядности, вот как распределяются серверы между клиентами:

| Сервер | Region | 🇷🇺 RU | 🇨🇳 CN | 🇺🇸 US | 🇮🇱 IL | Без страны |
|--------|--------|--------|--------|--------|--------|------------|
| str1   | ""     | ❌     | ❌     | ❌     | ✅     | ✅         |
| str2   | ""     | ❌     | ❌     | ❌     | ✅     | ✅         |
| str9   | "RU"   | ✅     | ❌     | ❌     | ❌     | ❌         |
| str10  | "CN"   | ❌     | ✅     | ❌     | ❌     | ❌         |
| str11  | "US"   | ❌     | ❌     | ✅     | ❌     | ❌         |

**Выводы:**
- Глобальные серверы (`region: ""`) доступны **только** странам без региональных серверов
- Региональные серверы доступны **только** своим клиентам
- **Если у страны есть региональные серверы, глобальные для нее исключены**
- Каждая страна получает **ИЛИ** свои региональные, **ИЛИ** глобальные (не вместе!)

## Логирование

Функция `getBestServerForCountry` записывает в лог следующую информацию:
- Выбранный сервер
- DNS сервера
- Количество сессий
- Регион сервера
- Код страны клиента

Пример лога:
```
DEBUG Selected server for request server=str9 dns=str9.example.com sessions=5 region=RU country_code=RU
```

## Обратная совместимость

Все изменения обратно совместимы:
- Поле `region` опционально (по умолчанию пустая строка = глобальный сервер)
- Функция `getBestServer()` продолжает работать без изменений
- GET `/server` работает без учета региона
- Старые конфигурации без поля `region` продолжат работать
- **Универсальная логика** - не требует изменений кода при добавлении новых стран

## Выделенные серверы по подсетям (`networks`)

Сервер можно закрепить за подсетями клиентов (CIDR):

```json
"str12": {
  "name": "str12",
  "dns": "str12.example.com",
  "enable": true,
  "online": true,
  "region": "",
  "networks": ["192.0.2.0/28", "198.51.100.16/28"]
}
```

- Сервер с непустым `networks` **эксклюзивный**: его получают только клиенты, чей IP попадает в одну из подсетей. Поле `region` у такого сервера не учитывается.
- Приоритет выбора: **подсеть → регион (страна) → глобальные**.
- Если все выделенные серверы для подсети offline/disabled, клиент получает сервер по обычной логике (регион или глобальный).
- IP клиента берётся из поля `ip` в теле `POST /server`, если оно пустое, то из адреса запроса (`c.ClientIP()`).
- Некорректные CIDR пишутся в лог при загрузке и пропускаются; сервер при этом остаётся эксклюзивным.
- В логе выбор помечается `pool_type: network` и `matched_networks`.
